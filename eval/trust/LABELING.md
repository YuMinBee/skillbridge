# STAR 정답셋 라벨 규칙

> 대상 파일: `gold_star_dev.jsonl`, `gold_star_test.jsonl`(1차, `labeler:"A"`), `gold_star_b.jsonl`(2차, `labeler:"B"`).
> 이 문서만 보고 두 사람이 따로 라벨해도 같은 답이 나오도록 쓴다. 애매하면 **없음** 쪽으로 판정한다(엄격 기준).
> 모양은 [CONTRACTS 6절](../../docs/pivot/CONTRACTS.md). 문장은 전부 합성이다. 실제 이력서를 넣지 않는다.

## 1. 한 줄 요약

| 칸 | "있다"의 최소 조건 | 이것만 있으면 **없음** |
|---|---|---|
| S 상황 | 왜 이 일이 필요했는지 **문제·제약·배경** 하나가 구체적으로 적혀 있다 | 프로젝트 이름, 기간, 인원, "~를 주제로" |
| T 과제 | 글쓴이(또는 팀)가 **이루려던 목표나 맡은 책임**이 행동과 구분되어 적혀 있다 | "열심히 참여", "프로젝트를 진행" |
| A 행동 | **무엇을 어떻게 했는지** 동사 + 대상 + 방법(도구·절차·근거) | "주도했다", "혁신적으로 개선", "다양한 기술을 활용" |
| R 결과 | 행동 뒤에 **무엇이 어떻게 바뀌었는지** 관찰 가능한 결과(지표, 배포·사용, 받은 피드백) | "성공적으로 마쳤다", "큰 성과", "많은 것을 배웠다" |

추가 필드
- `quantified`: R이 있고, R에 **무엇을 잰 숫자인지 드러나는** 수치(%, 시간, 건수, 사용자 수, 금액)가 있으면 `true`. R이 없으면 항상 `false`.
- `my_role_clear`: 글쓴이 **본인이 한 행동**이 팀의 행동과 구분되면 `true`. "우리 팀은 ~했다"만 있으면 `false`.
  - 주어가 없는 이력서 문체("~를 구현했습니다")는 본인 행동으로 본다. 한국어 이력서는 주어를 빼고 쓰는 것이 보통이기 때문이다. 한 줄짜리라 팀 작업인지 알 수 없어 보여도, "우리 팀", "함께", "팀원들과"처럼 팀이 주어라는 표시가 없으면 본인으로 본다.
  - A가 `false`이면 `my_role_clear`도 `false`다(구분할 행동이 없다).

## 2. 칸별 판정 기준

### S 상황
- 있다: 해결해야 할 문제("주문이 몰리면 응답이 5초를 넘었다"), 제약("서버 예산이 월 3만 원"), 배경("수기 엑셀로 재고를 관리해 매주 오차가 났다").
- 없다: "졸업 프로젝트로 쇼핑몰을 만들었다", "4인 팀, 8주", "AI를 주제로 해커톤에 참가".
- 판정 팁: 이 문장을 지워도 "왜 이 일을 했는가"가 그대로라면 S가 아니다.

예시
- ✅ "동아리 회비를 카톡으로 걷다 보니 누가 냈는지 매달 다시 확인해야 했다." (배경 + 문제)
- ❌ "2025년 2학기 캡스톤디자인에서 4명이 웹 서비스를 개발했다." (이름·기간·인원뿐)

### T 과제
- 있다: "결제 모듈 개발을 맡았다", "목표는 추론 시간을 1초 안으로 줄이는 것이었다", "제가 맡은 일은 데이터 정제 파이프라인이었다".
- 없다: 행동을 그대로 다시 쓴 것("API를 만드는 일을 했다"는 A로만 본다), "열심히 참여했다", "리더 역할을 했다"(무엇을 책임졌는지 없음).
- 팀 목표("팀 목표는 2주 안에 MVP 배포")도 T로 인정한다. 본인 몫이 안 보이면 `my_role_clear:false`로 따로 표시한다.

예시
- ✅ "저는 백엔드 중 인증과 권한 관리를 맡았습니다."
- ❌ "팀장으로서 프로젝트 전반을 이끌었습니다." (무엇을 이루려 했는지 없음)

### A 행동
- 있다: 동사 + 대상 + 방법이 모두 있다. "자주 조회되는 상품 목록을 Redis에 캐시했다", "결측치가 30% 넘는 열은 버리고 나머지는 중앙값으로 채웠다".
- 도구 이름만 나열("Spring Boot, MySQL, Docker 사용")은 A가 아니다. 도구를 **무엇에** 썼는지 있어야 한다.
- "개발했다", "구현했다"도 대상이 구체적이면 인정한다: "Spring Boot로 게시글 CRUD API를 구현했다" ✅ / "백엔드를 개발했다" ❌.
- 꾸밈말만 있는 문장은 몇 개가 있어도 A 없음: "주도적으로 혁신을 이끌었다", "최신 기술을 적극 도입했다".
- 팀이 주어인 행동("우리 팀은 ~를 만들었다", "함께 ~를 분석했다")도 동사 + 대상 + 방법이 있으면 A로 인정한다. 본인 몫이 드러나는지는 `my_role_clear`에서만 본다. (2026-11-20 팀장 판정, 1·2차 불일치 s071·s074)

예시
- ✅ "로그를 보니 같은 쿼리가 페이지마다 20번 나가서, JPA fetch join으로 한 번에 가져오게 바꿨다."
- ❌ "적극적인 자세로 다양한 기술을 활용해 문제를 해결했습니다."

### R 결과
- 있다: 지표 변화("응답 시간 3.2초 → 0.4초"), 실제 사용("동아리원 40명이 매달 사용"), 산출물이 쓰임("학과 공식 신청 시스템으로 채택"), 구체적 피드백("고객사 담당자가 정산 오류가 사라졌다고 확인").
- 수상은 결과로 인정한다("교내 해커톤 우수상"). 단 `quantified`는 순위만으로는 `false`.
- 없다: "성공적으로 마무리", "좋은 평가를 받았다"(누가, 무엇에 대해인지 없음), "많이 성장했다", 앞으로의 계획.
- 비교 대상이 없는 단일 지표도, 무엇을 잰 숫자인지 드러나면 R이다(예: "모델 RMSE는 0.91이었다", "테스트 정확도는 86%였다"). 결과가 **있는지**만 본다. 결과가 **좋은지**(비교가 없어 설득력이 약한지)는 라벨이 아니라 점수에서 다룬다.
- 판단이 어려우면 면접관이 "그래서 결과가 어땠어요?"라고 물었을 때 그 문장이 대답이 되는지 본다. "0.91 나왔습니다"는 대답이 되고, "많이 배웠습니다", "대성공이었습니다"는 대답이 안 된다.
- 기술 지표(RMSE, F1, mAP, 재현율 등)는 지표 이름이 있으면 무엇을 잰 숫자인지 드러난 것으로 본다. 라벨러가 지표 뜻을 몰라도 된다.
- **무엇을 잰 숫자인지 모르는 수치는 R이 아니다**: "팀 성과를 200% 끌어올렸다", "효율이 크게 향상(3배)" → 무엇의 효율인지 없으면 R 없음. 꾸민 말 함정의 핵심 기준이다.

예시
- ✅ "배포 후 한 달 동안 예약 중복이 0건이었고, 이전 학기에는 12건이었다." (quantified: true)
- ❌ "그 결과 프로젝트는 대성공을 거두었고 팀 전체의 역량이 비약적으로 향상되었습니다."

## 3. case 정의 (정답셋을 만들 때 의도한 유형)

case는 **만들 때의 의도**다. 라벨은 case와 무관하게 위 기준으로 문장을 보고 판정한다. 2차 라벨러에게는 case를 보여 주지 않는다.

| case | 의도 | 보통 라벨 |
|---|---|---|
| `full` | 네 칸이 다 있음 | S·T·A·R 있음, quantified 대부분 true |
| `no_R` | 행동까지만 있고 결과가 없음/모호함 | R 없음 |
| `no_T` | 목표·맡은 일이 안 드러남 | T 없음 |
| `inflated` | 꾸밈말·출처 없는 숫자만, 구체 행동·결과 없음 | A·R 없음 (S·T는 있을 수 있음) |
| `team_vague` | "우리 팀은"만 있고 본인 몫이 안 보임 | 칸은 있을 수 있음, `my_role_clear:false` |
| `short` | 한두 문장 | 대부분 칸 없음 |

## 4. 라벨 절차

1. 문단을 한 번 다 읽는다.
2. S → T → A → R 순서로 "있다"의 최소 조건을 만족하는 **문장 하나**를 찾는다. 찾으면 `true`, 못 찾으면 `false`.
3. R이 `true`일 때만 `quantified`를 본다.
4. `my_role_clear`를 본다.
5. 15초 넘게 망설이면 `false`로 하고 `note`에 이유를 적는다(나중에 규칙을 고칠 근거).

### 2차 라벨(사람 A–B 일치도)
- `gold_star_b.todo.jsonl`(id·text만 있는 빈 시트)에서 시작한다. **1차 라벨 파일(`gold_star_dev/test.jsonl`)은 열지 않는다.**
- 다 채우면 `gold_star_b.jsonl`로 저장하고 `labeler:"B"`로 둔다. `metrics.py`가 칸별 κ와 정확도를 계산한다.
- 불일치는 끝난 뒤 둘이 같이 보고, 규칙 문서를 고칠 일이면 이 문서에 날짜와 함께 적는다. **정답셋 라벨은 κ 계산 뒤에만 고친다.**

## 5. 파일 모양

```json
{"id": "s001", "text": "문단", "case": "full", "job_family": "backend",
 "slots": {"S": true, "T": true, "A": true, "R": true}, "quantified": true, "my_role_clear": true,
 "labeler": "A", "reviewed": false, "note": ""}
```
- CONTRACTS 6절 필드에 `job_family`·`my_role_clear`·`reviewed`·`note`를 더했다(읽는 쪽은 무시해도 된다).
- `reviewed:false` = Claude가 만든 초안 라벨. 1차 라벨러(김채희)가 문단을 읽고 이 문서 기준으로 확인하면 `true`로 바꾼다. **발표 숫자는 전부 `reviewed:true`가 된 뒤에만 낸다.** (평가 대상과 같은 계열 모델이 붙인 라벨을 그대로 정답으로 쓰면 편향이 생긴다.)
- dev(30%)는 T1·T2가 프롬프트를 맞출 때 써도 된다. test(70%)는 T3만 열고 마지막에 한 번 돌린다.

## 6. 바뀐 기록
- 2026-11-17 첫 판 (김채희 + Claude).
- 2026-11-17 dev 30개 1차 검토 완료(김채희, 라벨 수정 0). s076·s082에서 "한 줄만으로는 혼자 했는지 모르겠다"는 의견이 나와 논의했고, 주어 없는 이력서 문체는 본인으로 보는 규칙을 유지하기로 했다(위 `my_role_clear` 설명에 이유 추가).
- 2026-11-17 test 60개 1차 검토 완료(김채희, 라벨 수정 0). s075("모델 RMSE는 0.91이었다")가 비교 없는 숫자도 결과인지 애매하다는 의견이 나와, R 기준에 "비교 없는 단일 지표도 R", "결과가 어땠어요? 질문", "기술 지표 이름" 세 줄을 추가했다. 라벨은 바뀌지 않았다.
- 주의: 1차 검토는 Claude 초안 라벨과 근거를 보면서 했으므로 초안 쪽으로 끌렸을 수 있다. 2차 라벨(정답을 보지 않음)에서 많이 어긋나는 글은 다시 본다.
