# 전면 수정 계획: 근거로 답하는 취업 역량 RAG (2026-11-17)

> 11-17 멘토링 후 방향을 바꾼다. 이 문서가 기준이고, 예전 문서(DEMO_SCRIPT·SCORECARD·EVIDENCE_POSTING_GAP)는 이 문서와 다르면 이 문서를 따른다.
> 팀원 네 명이 각자 Claude Code를 돌린다. 자기 트랙 문서(`T1`~`T4`)와 [CONTRACTS.md](CONTRACTS.md)만 읽으면 시작할 수 있게 썼다.

## 1. 한 줄

**"ChatGPT나 Claude에 그냥 물으면 그럴듯하게 답한다. 우리는 공개 공식 자료에서 근거를 찾아 인용하고, 근거가 없으면 답하지 않는다. 그 신뢰도를 숫자로 보여 준다."**

기능을 늘리지 않는다. 같은 질문에 **기존 방식(LLM 단독, 단순 RAG)보다 믿을 만하다**는 것을 측정해서 보여 준다.

## 2. 멘토링 메모 → 우리가 할 일

| 멘토 메모 | 반영 |
|---|---|
| 경우의 수에 따라 정답을 판단해야 함 | 평가 질문을 **유형 7개**로 나눠 유형별로 점수를 낸다(4절). "답할 수 없는 질문에는 답하지 않는가"까지 정답으로 본다 |
| 성능 수치, 근거가 있어야 함 | 검색(Recall@5·MRR·nDCG), 생성(근거 일치율·인용 정확도·거부 정확도), 지연·비용. 모두 95% 구간 |
| 기업이 넣어주는 기준 ✕, 기술 블로그 ✕ | 실무 기준은 **NCS(국가직무능력표준) 능력단위**, 직업정보(커리어넷·워크넷)로 바꾼다. 기업 콘솔·블로그 갭(45.6%)은 발표에서 뺀다 |
| GPT·Claude는 이 정도지만 우리는 특화된 답 | 같은 질문 세트로 **LLM 단독 / 단순 RAG / 우리 방식** 3개를 비교한 표가 발표의 중심이다 |
| 슈퍼바이저 패턴, 토큰 비용, 코스트 계산 에이전트 | 슈퍼바이저가 하위 에이전트(검색·진단·과정·검증·비용)를 부른다. 비용 에이전트가 요청마다 토큰·금액을 집계하고, 예산을 넘으면 멈춘다 |
| 중단해도 내부에선 동작, 긴 응답 시간 | 질문은 **작업(job)**으로 접수한다. 브라우저를 닫아도 서버에서 계속 돌고, 다시 열면 결과가 있다 |
| 기능보단 신뢰성, 기존보다 나아지면 됨 | 새 기능보다 측정과 비교. 개선은 구간이 0을 포함하지 않을 때만 "개선"이라고 쓴다(규칙 12) |
| AWS 안에서는 이것보다 뛰어난 기술은 없다 | Bedrock KB(S3 Vectors), 임베딩 모델 비교, Rerank, Guardrails 근거 확인(contextual grounding), Bedrock RAG 평가 작업. **AWS 관리형 조합 중 최선을 실험으로 골랐다**고 말할 수 있게 한다 |

## 4. 평가: 경우의 수별 정답

질문 유형(`case`)은 7개다. 유형마다 최소 15문항, 합계 100문항 이상을 목표로 한다.

| case | 뜻 | 정답 조건 |
|---|---|---|
| C1 단일 근거 | 문서 하나에 답이 있다 | 정답 문서 검색, 핵심 사실 일치, 인용 |
| C2 다중 근거 | 2개 이상을 합쳐야 한다(예: NCS 기준 + 과정) | 필요한 문서 모두 검색 |
| C3 근거 없음 | 코퍼스에 답이 없다 | **답하지 않고** "근거 없음"이라고 말함 |
| C4 범위 밖 | 합격 가능성·연봉 예측처럼 하면 안 되는 질문 | 거부하고 이유 안내 |
| C5 시점·충돌 | 마감된 공고, 서로 다른 기준 | 최신·유효 자료를 고르고 차이를 밝힘 |
| C6 조건·수치 | 지역, 마감일, 국비 여부, 수강료, 시간 | 숫자가 정확함 |
| C7 함정 | 없는 과정·자격증 이름을 섞은 질문 | "그런 과정은 카탈로그에 없음" |

- 정답셋은 T3만 만든다. **dev 30% / test 70%**로 나눈다. T2는 dev로만 튜닝하고 test는 마지막에 한 번 돌린다(과적합 방지, 규칙 9).
- 비교 대상 3개: ① LLM 단독(같은 모델, 검색 없음) ② 단순 RAG(벡터 top-5 → 답) ③ 우리 방식(하이브리드+재랭킹+검증+거부).

## 5. RAG 실험: 숫자로 고른다

T2가 돌린다. 임베딩은 Bedrock으로 한 번만 계산해 로컬에 캐시하고, 조합 실험은 로컬에서 빠르게 한다. 고른 조합만 Bedrock KB(S3 Vectors)에 올린다.

| 축 | 후보 |
|---|---|
| 청크 크기(토큰) | 200 / 300 / 500 / 1000, 겹침 0·15% · 계층형(부모 1500·자식 300) · 문서 구조 단위(NCS 수행준거 한 줄 = 청크 하나) |
| 임베딩 모델 | Titan Text Embeddings V2(256·512·1024차원), Cohere Embed Multilingual(서울 리전 제공 여부 확인) |
| 검색 | 벡터만 / BM25만 / 하이브리드(RRF) |
| 재랭킹 | 없음 / Bedrock Rerank(서울 제공 여부 확인) / Haiku 재랭킹 |
| 벡터 저장소 | 로컬 정확 검색(기준) vs S3 Vectors(근사). 재현율 손실, 지연, 월 비용 |

- **토큰 길이**: 임베딩 모델마다 입력 상한이 다르다(Titan V2는 길게, Cohere는 짧게 받음 → 정확한 값은 실험 전에 문서로 확인). 상한을 넘는 청크는 잘려서 검색 품질이 떨어진다. "청크 길이 × 모델 상한"이 결과에 미친 영향을 그래프 하나로 보여 준다.
- 결과는 `eval/rag/results_retrieval.json`과 표 하나로 남긴다. 비용은 실제 토큰 수 × 공시 단가로 계산한다.

## 6. 구조: 슈퍼바이저와 하위 에이전트

```
질문 → POST /api/ask → job_id (즉시 반환)
         └─ 서버에서 계속 실행 (브라우저를 닫아도 됨)
            Supervisor(Haiku): 질문 유형(C1~C7) 분류 → 계획 → 하위 에이전트 호출
              ├ Retriever : 질의 재작성 → 하이브리드 검색 → 재랭킹 → 근거 묶음
              ├ Diagnose  : 기존 규칙 점수(score.py). 점수는 규칙으로만 (규칙 8)
              ├ Course    : 고용24 카탈로그에서만 과정 선택 (규칙 6)
              ├ Verifier  : 문장별 인용 확인 + Guardrails 근거 확인 → 실패하면 한 번 다시 쓰거나 "근거 없음"
              └ Cost      : 단계별 토큰·금액 집계, 요청 예산 초과 시 중단, 사용자 N명 월 비용 추정
GET /api/jobs/{id} → 상태 · 단계별 trace · 근거 · 비용
```

- 에이전트는 Bedrock Converse 도구 호출로 직접 만든다(단계별 trace와 비용을 그대로 보여 주기 위해). Bedrock Agents의 멀티 에이전트(슈퍼바이저 모드)는 대안으로 비교만 한다. 바꾸면 `DECISIONS.md`에 적는다.
- 작업 실행: 로컬은 백그라운드 스레드, 배포는 Lambda 비동기 자기 호출 + DynamoDB `JOB#` 항목.

## 7. 남기는 것 / 빼는 것

- 남김: 규칙 점수(`score.py`), 추출·정규화(`extract`·`normalize`), 고용24 카탈로그, Guardrail PII, 방문자 가드(`guards/`), 배포(`infra/`), 기존 평가 결과(이력서 오탐률 7.4% 등은 보조 근거로 사용 가능).
- 빼거나 숨김: 기업 콘솔·시뮬레이터 탭, 기업 E~H 현업 청취 기준, 블로그 갭 45.6%, 기업 KB의 tenant 기능(코드는 남기되 발표에서 안 씀).
- 코드를 지우지 않는다. 화면에서 숨기고, 발표에서 말하지 않는다.
