# 전면 수정 계획 (2026-11-17 멘토링 후)

> 이 문서가 기준이다. 예전 문서(SCORECARD·EVIDENCE_POSTING_GAP 등)와 다르면 이 문서를 따른다.
> 네 명이 각자 Claude Code를 돌린다. 자기 트랙 문서(`T1`~`T4`)와 [CONTRACTS.md](CONTRACTS.md)만 읽으면 시작할 수 있다.

## 1. 우리가 할 말

> **웹 GPT·Claude에 "내 역량 분석하고 과제 추천해 줘"라고 하면 여기까지다. 같은 Claude 모델을 AWS 안에서 시스템으로 돌리면, ○○% 정확도로 강점을 진단하고 근거가 붙은 과제를 추천한다.**

- 모델이 같다. 차이는 전부 **시스템**에서 나온다. 그래서 차이를 숫자로 보여 줄 수 있다.
- 기능을 늘리지 않는다. **신뢰성**(정확도·일관성·근거)을 측정해서 보여 준다.
- 판정 기준은 이미 인정받은 방법을 쓴다: 강점은 **STAR**(기업 역량면접 BEI의 경험 평가 방식), 역량은 **NCS**(국가직무능력표준).

## 2. 발표 순서: 문제 → 숫자 → 근거 → (마지막에) 기술

| # | 슬라이드 | 내용 |
|---|---|---|
| 1 | 이게 안 된다 | 웹 Claude에 같은 이력서로 "역량 분석하고 과제 추천해 줘". 일반론·지어낸 과정·돌릴 때마다 다른 답에 표시 |
| 2 | 그래서 | 취준생이 믿을지 말지 스스로 판단해야 한다 |
| 3 | **우리는 이 정확도로 한다** | 큰 숫자 2~3개, 옆에 웹 방식 숫자 (4절의 지표) |
| 4 | 근거가 있다 | 추천 한 줄 → 이력서 원문 문장 · NCS 기준 · 고용24 과정 링크. 근거 없으면 답하지 않음 |
| 5 | 기준도 검증된 것 | STAR, NCS. 사람 평가자끼리 일치하는 만큼 시스템도 사람과 일치한다 |
| 6 | 시연 | 한 이력서로 처음부터 끝까지 |
| 7 | 어떻게 가능했나 | 여기서 처음 기술: AWS 구조도, RAG 조합 실험표(임베딩·청크 토큰 길이·검색 방식) |
| 8 | 한계 | 합격 예측 안 함, 민간 공고 API 승인 대기 등 |

**3번 슬라이드의 숫자가 발표 전체를 받친다.** 그래서 T3(정답셋·평가)가 가장 급하다. 숫자는 실제로 잰 값만, 구간이 0을 포함하면 3번에 올리지 않는다(규칙 12).

## 3. 기능 구조

```
입력: 이력서(경험) + 지원 직군 (+ 선택: 공고 붙여 넣기)
 │  POST /api/analyze → job_id 즉시 반환. 브라우저를 닫아도 서버에서 끝까지 실행
 ▼
Supervisor ─ 단계 계획, 실패 시 폴백, 예산 확인
 ├① 강점 진단 (STAR)      경험 단락별로 S·T·A·R 칸을 채우고 칸마다 이력서 원문 인용.
 │                        인용이 원문에 없으면 그 칸은 '없음'. 점수는 규칙(칸 수·수치 성과·내 역할)
 ├② 역량 연결 (NCS)       직군의 NCS 능력단위·수행준거를 검색(RAG) → 보유/부분/없음 (기존 규칙 점수)
 ├③ 과제 추천 (RAG)       갭과 STAR 빈칸 → NCS 수행준거 근거로 '증명 과제' + 고용24 과정(카탈로그에 있는 것만)
 ├  Verifier              모든 문장에 인용이 있는지, 인용 내용이 맞는지. 실패하면 한 번 다시, 또 실패하면 '근거 없음'
 └  Cost                  단계별 토큰·금액, 요청 예산 초과 시 남은 단계 생략, 사용자 N명 월 비용 추정
 ▼
GET /api/jobs/{id} → 진행 상태 · 강점 · 갭 · 추천 · 근거 · 비용
```

기존 코드에서 쓰는 것: `extract`·`normalize`(스킬 추출), `score.py`(규칙 점수), `recommend.py`·고용24 카탈로그, Guardrail PII, `guards/`, `infra/`.
화면·발표에서 빼는 것(코드는 유지): 기업 콘솔·시뮬레이터, 기업 E~H, 블로그 갭 45.6%, 시장 분석 탭.

## 4. 3번 슬라이드에 올릴 숫자 후보

비교 대상은 같은 이력서·같은 모델이다. **웹 방식** = Bedrock 같은 Claude 모델 + 프롬프트 "내 역량 분석하고 과제 추천해 줘" 한 번(검색·규칙·검증 없음). 슬라이드 1의 화면은 실제 웹 Claude 캡처를 쓴다.

| 지표 | 뜻 | 측정 |
|---|---|---|
| STAR 판정 일치도 | 경험의 S·T·A·R 칸 유무를 사람 라벨과 비교 | 정확도, κ. **사람 A–B 일치도와 나란히** |
| 없는 근거 생성률 | 이력서에 없는 경험·성과를 있다고 한 비율 | 판정 문장 중 원문에서 확인 안 되는 비율 |
| 지어낸 과정 비율 | 추천 과정 중 고용24 카탈로그에 없는 이름 | 카탈로그 대조(규칙) |
| 일관성 | 같은 입력 5번 → 같은 강점·갭·추천 1순위 | 일치율 |
| 꾸민 말 강건성 | "혁신적으로 주도" 같은 말만 있고 행동·결과 없는 글에 높은 강점을 주지 않는가 | 함정 세트 오판정률 |
| 추천 근거 적합도 | 추천 과제가 실제 갭·NCS 수행준거와 맞는가 | 사람 판정(블라인드) |
| 블라인드 선호 | 현직자·멘토·취준생 5~10명이 이름 가린 두 결과 중 더 믿을 만한 쪽 | 설문 |

모든 수치는 `[값, 95% 구간 하한, 상한]`. 7번 슬라이드용으로 검색 지표(Recall@5·MRR·nDCG, 지연, 비용)를 따로 낸다.

## 4-1. 원칙: 모든 구성 요소는 "왜 좋은지"를 숫자로 (팀장 2026-11-17)

기능 하나를 넣을 때마다 **비교 대상과 숫자**가 있어야 한다. 숫자가 없으면 발표에서 말하지 않는다.

| 구성 요소 | 주장 | 숫자 | 비교 대상 | 담당 |
|---|---|---|---|---|
| STAR 진단 | 사람처럼 판정한다 | 칸 정확도·κ | 사람 A–B 일치도, 웹 방식 | T3 |
| 원문 인용 강제 | 지어내지 않는다 | 없는 근거 생성률 | 웹 방식 | T3 |
| 규칙 점수 | 같은 입력이면 같은 결과 | 5회 일관성 | 웹 방식 | T3 |
| 꾸민 말 규칙 | 말만 번지르르한 글에 속지 않는다 | 꾸민 말 세트 오판정률 | 웹 방식 | T3 |
| 과정 카탈로그 대조 | 없는 과정을 추천하지 않는다 | 지어낸 과정 비율 | 웹 방식 | T3 |
| 공고 출처(민간+잡알리오 반반) | 한쪽에 치우치지 않는다 | 출처별 기준 차이, 반반 vs 합산 시 순위 상관 | 민간만 / 잡알리오만 | T1 |
| 임베딩 모델 | 이 모델이 한국어 NCS 검색에 낫다 | Recall@5·MRR·비용 | Titan 256/512/1024 vs Cohere v4 | T2 |
| 청크 길이 | 이 길이가 최적 | Recall@5 vs 청크 토큰 | 200/300/500/1000 | T2 |
| 하이브리드·재랭킹 | 섞으면 더 찾는다 | Recall@5 증가분(구간) | 벡터만 | T2 |
| 검증 에이전트 | 잘못된 근거를 걸러낸다 | 검증 전후 오류율 | 검증 끔 | T1 |
| 비동기 job | 오래 걸려도 끊기지 않는다 | 완료율, p95 시간 | 동기 요청(타임아웃) | T1 |
| 비용 에이전트 | 싸다 | 분석 1건 $, 사용자 1,000명 월 $ | 웹 구독료 | T1 |
| 개인정보 | 원문을 남기지 않는다 | 저장 항목 0, 마스킹 테스트 | — | T1 |
