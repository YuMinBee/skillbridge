## 슬라이드별 대본

### 1. 표지 · 0:30

06팀 역량다리입니다. 저희 과제는 **AWS 클라우드 기반 채용시장 기술역량 자동 분석 및 교육과정 추천 AI 에이전트 개발**입니다.  
취준생은 이미 자기 역량을 AI에게 묻고 있습니다.  
**저희는 기능이 많은 서비스가 아니라, 믿고 쓸 수 있는 서비스를 만들었습니다.** 같은 Claude를 AWS 안에서 시스템으로 돌려, 모든 판정에 확인할 수 있는 근거를 붙였습니다.

### 2. 문제 — 웹 Claude 답 · 1:30

**저희는 왜 에이전트를 써야 할까요?**  
역량 분석은 웹 Claude에 물어봐도 됩니다. 그래서 직접 해 봤습니다.

시연용 자소서를 웹 Claude에 넣고 "역량 분석하고 과제 추천해 줘"라고 세 번 물었습니다.  
강점 판단은 세 번 모두 같았습니다. **판단은 좋습니다.**  
그런데 추천 과정은 매번 달랐습니다. 대부분 이미 마감된 선발형 과정이었고, 개강일까지 알려 준 추천은 세 번 중 한 번뿐이었습니다.

취준생 한 명이라면 몇 번 더 물어보고 직접 찾아보면 됩니다.  
**그런데 이걸 취업센터나 부트캠프가 상담에 쓴다면 어떨까요?**

학생 자소서를 개인 웹 채팅에 넣기 어렵고,  
수백 명을 상담하려면 **누가 언제 넣어도 같은 답, 확인할 수 있는 근거, 남는 기록**이 필요합니다.  
**그래서 에이전트입니다.** 기관 환경 안에서 돌고, 같은 입력에 같은 답과 근거를 남깁니다.  
저희는 그 에이전트를 단계로 나누고, 단계마다 확인 장치를 붙였습니다.

- 표는 웹 검색이 켜진 3번이다. 다른 계정으로 검색 없이 3번 더 물었을 때도 판단은 같았고, 개강일·링크는 하나도 없었다(질문이 오면 답한다).
- "1번"은 답 1의 쌍용 과정(개강일 12/21)이다. 우리 고용24 목록에서는 확인되지 않았으므로 "신청 가능했다"고 단정하지 않는다.

### 3. 문제 — 설문 · 0:30

취준생 29명에게 물었더니 **86%가 모르는 기술을 생성형 AI로 확인**합니다. 검색보다 많습니다.  
믿으려면 근거가 된 공고 문장과 추천 이유가 필요하다고 답했습니다.  
그래서 이 두 가지를 기능으로 만들었습니다.

### 4. 해결 · 1:45

먼저 **채용 시장을 자동으로 분석**합니다. 지원 분야(민간·공공)의 직군별 공고에서 요구 기술을 뽑아 비율을 셉니다.  
그다음 자소서와 GitHub에서 **내 기술**을 뽑아 시장 기준과 비교해 **부족한 역량**을 찾습니다. 예를 들어 "민간 백엔드 공고 45건 중 몇 건이 AWS를 요구한다"는 건수와, 그 공고 문장과 내 자소서 문장을 나란히 보여 줍니다. (건수는 화면에 나온 숫자를 그대로 읽는다)  
부족한 역량은 **고용24에 실제로 있는 교육과정과 과제**로 채웁니다. 맞는 과정이 없으면 "맞는 과정 없음"이라고 말합니다.

여기에 저희는 한 가지를 더했습니다. 그 기술을 쓴 경험이 **면접에서 통할 만큼 근거가 있는지**를 기업 역량면접 기준인 **STAR**로 판정합니다. 칸마다 자소서 원문 문장만 쓰고, 없으면 빈칸입니다.

- 과제명 순서(채용시장 기술역량 자동 분석 → 교육과정 추천)대로 말하고, STAR는 '우리가 더한 것'으로 말한다
- 화면의 직군 순위·공고 건수 줄, 초록 칸(원문 인용)과 회색 칸(없음)을 손으로 짚는다

## 예상 질문

### 비교와 숫자

**Q. 웹 비교가 공정한가요? 실제 웹이 아니라 API로 흉내 낸 것 아닌가요?**  
같은 Bedrock Claude Sonnet 4.6에 웹 채팅에 칠 문장을 그대로 넣어 재현했습니다(temperature 0과 1 둘 다). 실제 웹 캡처 3회는 2장에서 따로 보여 드렸습니다.  
→ eval/trust/baseline_web.py, docs/pivot/captures/

**Q. 프롬프트를 잘 쓰면 되지 않나요?**  
우리 칸 기준까지 준 웹 ③은 정확도 94.7% vs 96.2%로 **차이가 유의하지 않습니다.** 하지만 없는 근거 6.7% vs 2.1%, 5회 일치 88% vs 100%는 유의하게 차이 납니다.  
→ 부록 '웹 세 방식 전체 표', eval/trust/report.md

**Q. 100% 일치는 캐시 때문 아닌가요?**  
평가할 때는 캐시를 껐습니다. 원문 대조와 규칙 점수 덕분입니다. → eval/trust/run_ours.py

**Q. 점수를 맞춘 것 아닌가요?**  
기준은 dev로만 고쳤고, test는 11-20에 한 번만 돌렸습니다. → eval/trust/report.md

### 정답과 평가

**Q. 정답은 누가 만들었나요?**  
합성 단락 90개(dev 30 · test 60)를 1차 라벨러가 전부 검토했습니다. dev 30개는 다른 사람이 따로 2차 라벨을 달았고, 사람끼리 89%(κ 0.78) 일치했습니다.  
→ eval/trust/LABELING.md, eval/trust/disagreements_ab.md

**Q. 사람보다 낫다는 건가요?**  
아닙니다. 사람 89%는 dev, 저희 96%는 test라 표본이 다릅니다. 사람끼리 맞는 수준만큼 일관되게 판정한다는 뜻입니다. → 8장

**Q. 합성 단락이면 쉬운 것 아닌가요?**  
맞습니다, 한계입니다(11장). 대신 꾸민 말, 빠진 칸 등 6가지 유형을 섞었습니다. → 부록 '평가 방법'

### 시스템과 운영

**Q. 이력서가 저장되거나 해외로 나가나요?**  
원문은 저장하지 않습니다. 결과(개인정보를 가린 뒤의 인용 문장 포함)만 DynamoDB에 24시간 캐시했다가 자동 삭제됩니다. 모델에 보내기 전에 서울 리전 Guardrails와 정규식으로 개인정보를 가리고, Cohere에는 역량 이름만 갑니다.  
→ backend/app/agents/star.py, DECISIONS.md

**Q. '에이전트 7개'는 결국 파이프라인 아닌가요?**  
맞습니다. 슈퍼바이저가 단계를 부르고, 한 단계가 실패하면 그 단계만 규칙으로 대신합니다. 과장하지 않고 "단계"라고 부릅니다. → backend/app/agents/supervisor.py

**Q. 왜 Bedrock Knowledge Base나 Agents를 안 썼나요?**  
숫자로 고르기 위해서입니다. 교육 검색은 임베딩 4종과 키워드 검색을 같은 질의 40개로 비교해서 골라야 했고, 그래서 검색을 직접 구현했습니다. 과정이 1,856개라 Lambda 메모리 검색으로 충분하고, 상시 과금도 없습니다.  
**옮기는 건 구조상 바로 됩니다.** 검색은 search(config=...) 한 곳으로 분리돼 있고, Bedrock Knowledge Base 호출 코드(adapters/kb.py)와 S3 Vectors로 KB를 만드는 스크립트(infra/build_kb.py)가 이미 있습니다. 이전 버전에서 실제로 KB를 만들고 데이터 격리까지 검증했습니다. 설정 하나를 바꾸고, 같은 평가로 다시 재서 비교하면 됩니다.  
Agents도 단계마다 독립 함수라 액션 그룹으로 감쌀 수 있습니다. 다만 순서를 고정하고 단계마다 검증하려고 슈퍼바이저는 코드로 두었습니다. 모델이 순서를 정하면 "5번 모두 같은 판정"을 보장하기 어렵습니다.  
→ backend/app/rag/retrieve.py, backend/app/adapters/kb.py, infra/build_kb.py, DECISIONS.md(11-17)

**Q. 기술역량을 정확히 뽑나요? (공고·자소서에서 기술 추출)**  
이번 평가(96 · 2 · 100)는 STAR 판정입니다. 기술 추출은 이전 단계에서 따로 쟀습니다. 가진 역량을 부족하다고 잘못 보는 비율을 23.4%에서 7.4%로 줄였고(차이 유의), 공고 추출 F1은 0.744 → 0.809였지만 30건이라 차이가 유의하지 않았습니다. 이전 버전 숫자라는 점을 함께 말합니다. → eval/report.md

**Q. 7단계인데 왜 Step Functions를 안 썼나요?**  
한 번에 20~30초면 끝나서, Lambda 하나가 자기 자신을 비동기로 불러 처리하는 게 가장 단순했습니다. 단계별 진행은 DynamoDB에 남겨 화면에 보여 줍니다. 단계가 길어지거나 사람 승인이 필요해지면 Step Functions로 옮길 수 있습니다.

**Q. 로그인 없이 공개 주소인데 보안은요?**  
심사·시연용이라 로그인을 두지 않은 대신 IP당 분당 8회, 시간당 20회, 동시 실행 2개, 요청당 비용 상한 $0.30을 걸었습니다. 원문은 저장하지 않고 Guardrails로 개인정보를 가립니다. 기관에 들어가면 Cognito 같은 로그인을 붙입니다.

**Q. 비용은요?**  
분석 1건에 약 $0.03~0.18이고, 요청 예산 $0.30 상한이 있으며, 상시 과금은 없습니다. 100명 × 4회 = 월 약 $70입니다.

**Q. 오래 걸리면요?**  
작업으로 접수해 서버에서 끝까지 돌립니다. 창을 닫았다 열어도 결과가 남고, 같은 문서는 두 번째부터 8초 안팎입니다. → eval/smoke_deploy.md

**Q. GitHub README를 본인이 쓴 건지 어떻게 아나요?**  
진위 판정이 아니라 "문서에 적힌 것" 기준이라는 걸 범위로 밝힙니다. 판정마다 원문 인용이 붙어 있어 사람이 확인할 수 있습니다.
